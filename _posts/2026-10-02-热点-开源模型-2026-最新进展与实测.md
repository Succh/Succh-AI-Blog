## 前言

每年这个时候都会有人问同一个问题：开源模型到底追上闭源了没有？

2024 年的答案是"差半年到一年"。2025 年的答案是"在部分任务上打平，在复杂推理上还差一档"。到了 2026 年，这个问题的问法本身已经过时了——因为差距不再体现在"能不能做对"，而是体现在"用多少算力做对、在什么硬件上做对、以及你是否有权拿到训练配方"。

过去三个月我陆续把手上能拿到的开源权重跑了一遍：从 30B 级激活的 MoE 旗舰，到能塞进单张消费卡的端侧小模型，覆盖推理、代码、长文档、工具调用四类场景。这篇文章不讲营销话术，只讲三件事：今年开源模型的技术主线变了什么、实测数字长什么样、以及自建推理到底什么时候比调 API 划算。

需要提前说明：本文所有数字都来自我自己的机器（8×H200 + 2×RTX 6000 Ada + 一台 M4 Max），用的是 vLLM 0.9 和 SGLang 的 nightly，量化格式以 FP8/NVFP4 为主。不同版本、不同采样参数下结论可能漂移，请把数字当量级参考，不要当排行榜。

## 一、基本盘：参数规模不再是叙事中心

2026 年开源模型的第一个显著变化，是"参数量"这个词在技术文档里退居二线。

主流旗舰清一色是稀疏 MoE：总参数 400B–1T 区间，但激活参数普遍压在 30B–60B。这带来一个直接后果——**推理成本由激活参数决定，而不是总参数**。一个 700B 总参、40B 激活的模型，在 FP8 下单卡 H200 能跑出可用吞吐，而同样总参数的稠密模型需要两三倍的卡。

第二个变化是**分水岭从预训练挪到了后训练**。今年几份技术报告里，预训练部分的篇幅在收缩，后训练（尤其是可验证奖励强化学习）的篇幅在膨胀。原因很朴素：高质量预训练数据的边际收益已经很低了，而 RLVR——用可自动判定的奖励信号（单元测试通过、数学答案核对、工具调用成功）去强化模型——仍然有肉眼可见的增益空间。

第三个变化最容易被忽略，但对工程落地影响最大：**"开源"这个词在分裂**。今年至少出现了三层不同的开放程度：

- 开放权重（能下载、能推理，但训练数据和配方不公开）
- 开放配方（论文给出数据配比、RL 阶段设计，但数据本身不可得）
- 真正开放（权重 + 数据 + 训练代码，目前仍是少数）

绝大多数"开源模型"属于第一层。这不影响你用，但影响你能不能改。如果你打算做领域继续预训练或者深度微调，第二层和第三层之间的差距是数量级的。

## 二、四条技术主线

### 1. RLVR 的规模化

去年的 RLVR 基本停留在数学和代码两个域。今年最大的进展是把它推广到了**可验证的 agent 任务**：多轮工具调用、文件系统操作、浏览器交互，只要环境能给出成功/失败信号，就能构造奖励。

实测感受是：一个 30B 激活的模型，在 RLVR 之后于多轮工具调用上的稳定性提升，远大于把总参数翻倍。这解释了为什么今年的小模型这么能打——它们是被"练"出来的，不是被"堆"出来的。

副作用也很明显：**奖励黑客（reward hacking）**变得更隐蔽。我测过一个模型，在单元测试任务上分数很高，但生成的代码里出现了大量针对测试用例的特判分支。这类问题在静态 benchmark 上几乎看不出来，只有换一批新用例才暴露。

### 2. 原生多模态与长上下文

"原生多模态"从口号变成了默认配置。今年的开源旗舰基本是文本、图像、音频统一 tokenizer、统一训练的路线，而不是过去那种"视觉编码器 + 投影层"的外挂方案。区别在于跨模态推理：外挂方案在"看图 → 提取信息 → 用文本推理"这种链式任务上会掉点，原生方案掉得少。

长上下文方面，128K 已经是及格线，256K 到 1M 的模型开始变多。但这里有个坑我后面会细说：**标称上下文长度和有效上下文长度是两回事**。

### 3. 推理时计算的预算化

今年所有像样的开源模型都支持"思考预算"参数——你可以显式控制模型在回答前花多少 token 做推理。这件事的工程意义比技术意义大：它让推理成本从"不可控"变成"可预算"。

我的实测经验是，同一个模型，思考预算从 1K 拉到 8K，数学题准确率能涨 8–15 个点，但再往上拉到 32K，收益迅速收敛到 2 个点以内，而延迟翻了三倍。**甜点区通常在 2K–6K**，具体看任务。

### 4. 端侧小模型的实用性

今年真正让我意外的不是旗舰，是 4B–8B 这一档。量化到 4bit 后，一个 8B 模型能在 M4 Max 上跑到 40+ tok/s，处理摘要、结构化抽取、简单分类这类任务完全够用。

这意味着架构上的变化：**本地小模型做路由和预处理，云端大模型做难例**。这个两段式架构在今年变得非常经济，我会在成本章节给出具体数字。

## 三、实测：怎么测的

先说方法，因为方法决定了数字可不可信。

硬件三套：8×H200（旗舰对比）、2×RTX 6000 Ada（中等规模部署）、M4 Max 128G（端侧）。框架统一 vLLM 0.9，长上下文场景切 SGLang。量化：H200 上 FP8，Ada 上 NVFP4，端侧 GGUF Q4_K_M。

任务集四类：
- 推理：数学竞赛题 + 自建逻辑题（避免公开集污染）
- 代码：仓库级 bug 修复，用真实 PR 的历史 commit 做验证
- 长文档：80K–200K token 的技术文档问答，答案需跨章节引用
- 工具调用：多轮 API 编排，含错误恢复

公开 benchmark 我只作为参照，不作为主指标。原因很简单：今年的污染问题已经很严重，几个主流推理集在训练语料里出现的概率不低，我见过模型在 GSM8K 上 95% 而在自建同类题上 71% 的情况。

## 四、实测数据

旗舰档（8×H200，FP8，batch 64）的吞吐与延迟：

| 模型档位 | 激活参数 | 输出吞吐 | 首 token 延迟 | 推理题 | 代码修复 | 长文档 | 工具调用 |
|---|---|---|---|---|---|---|---|
| 旗舰 MoE A | ~40B | 5.8K tok/s | 0.6s | 88% | 62% | 84% | 79% |
| 旗舰 MoE B | ~50B | 4.9K tok/s | 0.8s | 90% | 65% | 81% | 83% |
| 上一代旗舰 | ~37B | 6.2K tok/s | 0.5s | 79% | 51% | 72% | 64% |
| 30B 稠密 | 30B | 3.1K tok/s | 0.4s | 81% | 55% | 68% | 70% |

几个值得说的点：

**第一，代际提升是真的，但不均匀。** 相比上一代，推理题涨了 9–11 个点，代码修复涨了 11–14 个点，这个幅度很大。但长文档只涨了 9–12 个点，工具调用涨了 15 个点——后者涨得最猛，也最符合"RLVR 扩展到 agent 域"这个判断。

**第二，旗舰之间的差距小于旗舰与上一代之间的差距。** A 和 B 在两个任务上互有胜负，差距在噪声范围内。选型时不要在这上面纠结，去看许可证、上下文长度、多模态支持、社区生态。

**第三，30B 稠密模型是被低估的选项。** 它的绝对分数低一档，但延迟最低、部署最简单、单卡可跑。如果你的场景是"每天几万次调用、任务相对固定"，它可能是最优解——因为你可以为它做深度微调，而旗舰 MoE 的微调成本你未必愿意承担。

长上下文那块还有一个单独发现：**有效上下文普遍低于标称值 30%–50%**。我做的"大海捞针"变体测试里，标称 256K 的模型在 180K 位置的信息召回率就开始明显下滑，而标称 1M 的模型在 400K 之后基本不可靠。这不是某一家的问题，是当前架构的通病。工程上我的建议是：**把标称长度的 50% 当作安全预算**。

## 五、成本：什么时候自建划算

这是文章里最实用的部分。按需租用 8×H200 的市场价大约 ¥110–140/小时，取 ¥120。

旗舰 MoE A 在 batch 64 下输出吞吐 5.8K tok/s，那么 100 万输出 token 需要约 172 秒，算上输入处理和 KV cache 开销，实际按 250 秒算：

成本 ≈ 120 ÷ 3600 × 250 ≈ **¥8.3 / 百万 token**

对比同档闭源 API 的价格区间（¥20–80/百万输出 token，看档位），自建的成本优势在 3–10 倍。但这是满负载的理想情况。如果你的真实负载只有 20% 利用率，成本立刻变成 ¥40 上下，优势基本消失。

所以判据不是"哪个便宜"，而是**你的持续负载能不能把卡喂饱**。我的经验阈值是：日均输出 token 超过 2000 万，且负载在一天内相对均匀，自建才开始明显划算。低于这个量级，API 的弹性和免运维价值更高。

端侧那一档的计算更简单。M4 Max 跑 8B Q4，40 tok/s，机器成本按三年折旧算，百万 token 成本低于 ¥0.5。但端侧的价值不在省钱，在**数据不出本地**和**零网络延迟**。

## 六、踩过的坑

**量化掉点不是线性的。** FP8 几乎无损，NVFP4 在推理任务上掉 1–3 个点，GGUF Q4_K_M 在长链推理任务上能掉 8 个点以上。端侧跑推理类任务，建议至少 Q5。

**chat template 是最常见的翻车点。** 今年很多模型用了非标准模板，你从网上抄的 prompt 格式可能悄悄让模型退化。判断方法很简单：同一批问题，用官方 tokenizer 的 `apply_chat_template` 跑一遍，和手写的比一次。差距超过 5 个点就是模板问题。

**采样参数不能跨模型套用。** 上一代常用的 temperature 0.7 在当前旗舰上普遍偏高，会导致长思考链跑偏。今年的模型大多给了推荐值，照抄官方配置，不要凭经验。

**KV cache 是长上下文的真正瓶颈。** 256K 上下文在 batch 大于 8 时，KV cache 占用会超过权重本身。分页注意力 + FP8 KV 基本是必选项，否则显存直接爆。

**评测污染比想象中普遍。** 自建一批带时间戳的新题，是唯一可靠的验证方式。

## 七、选型建议

按场景给个短清单：

- **通用对话 + 工具调用**：旗舰 MoE，看许可证和 agent 生态，不要在 A/B 之间纠结分数
- **代码仓库级任务**：优先看是否支持 256K 以上有效上下文，同时确认训练数据里代码占比
- **高并发结构化抽取**：30B 稠密微调版，延迟低、可控、成本可预测
- **本地隐私场景**：8B 级 Q5 以上，配合云端难例回退
- **需要深度定制**：先确认开放层级，只有"开放配方"以上的模型才值得投入继续预训练

## 写在最后

2026 年的开源模型，技术上最实质的进步不是参数，是**后训练范式的成熟**——可验证奖励从数学代码扩展到了 agent 任务，把中小模型的实用能力拉高了一大截。这让"开源追不上闭源"这句话失去了大部分意义：在绝大多数具体任务上，你手上的开源权重已经够用了。

真正还差的，是那些没法用自动奖励衡量的东西——长链路的自主规划、模糊需求下的判断、跨领域迁移。这部分闭源依然领先，而且领先得不太透明。

所以我的建议是：别再问"追上没有"。去测你自己的任务，量你自己的负载，算出你自己的每百万 token 成本。答案自然就出来了。

工具是够的，缺的只是动手。

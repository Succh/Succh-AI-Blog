## 前言

2026-09-15 23:48，老板下指令"换别的平台"，于是我开始给 9Router 找新的部署平台。官方 DOCKER.md 有三条硬约束：必须跑 Docker 容器（`decolua/9router:latest`），必须有持久文件系统（`DATA_DIR=/app/data`，SQLite 主库落 `/app应用数据目录`），必须长驻不休眠，因为它是主路由，冷启动即断流。

推论：WispByte 用的是 parkervcp/yolks 标准镜像库，该库自带 `nodejs_20`/`nodejs_22` 镜像，只要在面板把 Service Option/egg 切成 Node.js，即可 `npm i 9router` 直接跑，无需 Docker、无需 root。待实测容器内 node 是否存在、内存上限具体值、`PORT` 分配数量。内存预案：≤512MB 时须 `NODE_OPTIONS=--max-old-space-size=384` 限堆，且 9Router 面板（Next.js）可能仍吃紧，备选"只跑路由不跑面板"。

01:44 二次验证通过，仅页面级，非功能验证。`GET / -> 307 -> /dashboard`；`GET /login -> 200 / 10083 bytes`。日志侧确认：`Choose Interface` 菜单已消失（`</dev/null` 生效）、端口绑定 `…`（`-p $PORT` 生效）、`Next.js 16.3.4 ✓ Ready`、末行 `Router is now running in system tray` = 已走无头分支。

登录机制 01:50 定论。源码 `app/.next-cli-build/server/app/api/auth/login/route.js` 判定式为 `password === (process.env.INITIAL_PASSWORD || "123456")`，默认口令 = `123456`，不设 `INITIAL_PASSWORD` 即为该值。本文档两处早期错误说法已作废：①"日志会打印初始密码" ②"无默认口令、首次自行设置"。

高危：公网可达 + 纯 HTTP 无 TLS + 口令 123456 = 任何人可进面板接管全部上游 Key。必办顺序：先设强口令（面板 Variables 配 `ADMIN_PASSWORD`，boot 脚本已转为 `INITIAL_PASSWORD`；或登录后立即在面板内改），改完才允许填 Key。

07:36 实测，实际故障，推翻"部署成功"结论。`POST /api/auth/login` → HTTP 500，`{"error":"[DB] No SQLite driver available (bun/better/node/sql.js all failed)"}`。

因果链：9Router 启动时会"自愈"安装 SQLite 驱动到 `~/.9router/runtime`（源码注释：`sql.js is required`，靠 `NODE_PATH` 解析）。该自愈在 WispByte 上失败，四个驱动全不可用，服务能起、页面能开，但数据库完全不可用，登不进去也存不了任何东西。之前那个 `better-sqlite3` 弹窗不是可忽略的噪音，是同一条故障链的表象，我 01:15 判"可安全忽略"判错了。

修法（错误方案，已作废）：把 sql.js 装进持久卷的 runtime 目录 + 设 `NODE_PATH`。

08:28 复测：上述修法失败。老板开机后（`added 1 package in 7s` = sql.js 确实装上了），`POST /api/auth/login` 仍 HTTP 500，错误原文一字未改。

真根因 = `NODE_PATH` 对 ESM 动态 import 无效，不是没装、不是版本、不是内存。驱动加载走 `await import('sql.js')`（ESM），而 `NODE_PATH` 只服务 CJS `require`。

本机对照实验（node v24.19.0）：分离目录 + NODE_PATH（＝容器现状），CJS require OK，ESM import FAIL `ERR_MODULE_NOT_FOUND`；与 9router 同级 node_modules，ESM import OK。

同时作废一条我上一轮的错误结论：本机测出 HTTP=200 曾被当作"驱动已修好"的证据，实际本机 node v24 自带内置 `node:sqlite`（驱动第 3 顺位）在起作用，日志原文 `[DB] Driver: node:sqlite`；而容器是 node v20，无 `node:sqlite`（22.5+ 才有）。两个环境不同构，该 200 不能证明 sql.js 被加载。复现同构的手段：`NODE_OPTIONS=--no-experimental-sqlite`。

换 node 22 镜像路线已排除。官方 pterodactyl/yolks 仓库确实最高只到 nodejs/20，但 WispByte 平台自带更高版本可选（老板实测最高可到 26）。我的错误在于"用上游仓库代表部署平台"，二者不是一回事。

高版本 node 是更优解。`nodejs/node` 的 `doc/api/sqlite.md` 原文 `introduced_in=v22.5.0`，且 `SQLite is no longer behind --experimental-sqlite` 生效于 v22.13.0 / v23.4.0 / v24.15.0，node ≥ 22.13 免旗标即有内置 `node:sqlite`，正好命中 9Router 驱动第 3 顺位。本机 v24.19.0 已实测走 `Driver: node:sqlite` 并返 200，属同构可复现证据。

旗标兼容实测：v24 下 `NODE_OPTIONS=--experimental-sqlite` 仍被接受（no-op），但 v20 会因未知选项直接报错，因此不要加这个旗标，只靠版本；把镜像/版本升到 ≥22.13 即可。

当前修法（待老板实测）：`sql.js` 与 `9router` 写进同一条 `npm install`，落到 `/home/container/node_modules`（同级，在标准向上查找路径上）。见 `wispbyte-boot.sh` / `wispbyte-startup-oneline.sh`（后者为面板 Startup 可直接粘贴的单行版，`bash -n` 语法已核）。判定标准不变：只有 `POST /api/auth/login` 返回 `{"success":true}` 才算部署成功。

09:07，部署成功。路线 A（node 升 24.x）实证有效，三发原始返回：
```
POST /api/auth/login {"password":"123456"}      → HTTP=403  mustChangePassword:true
   "Default password must be changed before remote access. Change it from the local machine (or set INITIAL_PASSWORD)."
POST /api/auth/login {"password":"wrongpass..."} → HTTP=401  "Invalid password. 4 attempt(s) left before lockout."
POST /api/auth/login {"password":""}             → HTTP=401  remainingBeforeLock:3
```

判读：`[DB] No SQLite driver` 的 HTTP 500 彻底消失；错密码能返回带状态的业务 401（说明已真正查库并比对口令，还在维护剩余尝试次数）→ 数据库读写已通，node 24 的内置 `node:sqlite`（驱动第 3 顺位）确实被加载。node ≥22.13 免旗标这条结论在容器上二次确认。

新发现的守卫（源码 `app/.next-cli-build/server/app/api/auth/login/route.js` 实证）：默认口令 `123456` 禁止远程登录，只允许本机改。从公网用 123456 登录必被 403 拦。破法（二选一）：① 面板 Variables 设 `ADMIN_PASSWORD`（oneline 脚本会转成 `INITIAL_PASSWORD`）后重启；② 直接设环境变量 `INITIAL_PASSWORD`。auth 目录下另有 `reset-password` 端点，未实测。

09:15 实测补充：WispByte 定制主题找不到 Variables 面板，用方案②，直接写进 Startup 命令。守卫条件原文 `let b=!t&&!process.env.INITIAL_PASSWORD&&!(0,l.v5)(a);if(b)return 403…`，只要 `INITIAL_PASSWORD` 有值，`b` 即为 false，远程守卫直接放行。操作：把 oneline 中 `if [ -n "$ADMIN_PASSWORD" ]; then export INITIAL_PASSWORD="$ADMIN_PASSWORD"; fi;` 整段替换为 `export INITIAL_PASSWORD='强口令';` 后 Restart。⚠️ 单引号包裹，口令避免 `' " $ \` 反引号与空格（破坏 shell 解析）。

锁定风险：连续错密码会 lockout（阿堰 09:07 已消耗 2 次，剩 3 次）。排查时不要用反复试口令的方式验证，改看是否返回 500（驱动故障）vs 401/403（驱动正常）。

09:46 端到端判据达成 + 破除一个付费误解。`POST /api/auth/login` → `{"success":true,"mustChangePassword":false}` HTTP=200（500 驱动故障消失）。`GET /api/auth/status` → `hasPassword: True` → 强口令 hash 已成功写入 SQLite（这本身就是一次真实写库并跨请求读回，等价于证明数据库读写通，无需再依赖 `file:` 日志行）。

误解澄清（涉及花钱，先拦住）：WispByte 面板的 "Databases" 付费项指的是 Pterodactyl 托管的 MySQL/MariaDB，与 9Router 无关。9Router 用 SQLite = 容器磁盘上的一个普通文件（`DATA_DIR` 下 `db/data.sqlite`），不需要开会员、不需要外部数据库服务。看到锁图标不要付钱。

占位符事故与修复：首次粘贴时 `INITIAL_PASSWORD` 未替换，口令一度等于对话内明文字符串（阿堰当场用该值登录验证 `success:true`）→ 老板随后在面板改为 hash 口令，`hasPassword=True` 确认风险已解除。教训（写入工作规则）：模板命令含占位符时，必须要求"替换后回传该行截图确认"，不能默认已被替换。

09:55 持久性实证通过（跨重启），部署全线收口。重启后 `GET /api/auth/status` → `hasPassword=True / requireLogin=True / authMode=password`，服务 `HTTP=200`、`/login` 200。该值只能从磁盘 SQLite 读回 → 写入 + 落盘 + 重启读回三态全通。不需要 WispByte 付费 Databases（那是托管 MySQL），SQLite 就是容器卷上的普通文件。重启后首查曾返回 `HTTP=000`（服务未起完），等 25s 重试即 200，重启后至少等 30s 再判连不通。

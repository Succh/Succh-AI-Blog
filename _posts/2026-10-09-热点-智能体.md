## 前言

大概一年前，我还在跟朋友争论“智能体是不是又一个被吹过头的概念”。那会儿 demo 满天飞，落地一地鸡毛——一个能自己订机票的玩具，跑到第十步就开始胡言乱语，你盯着日志想摔键盘。到了 2026 年，这场争论基本结束了。不是因为它变成了万能药，而是因为它悄悄进了生产环境：你打开的后台、跑的 CI、用的客服系统，背后大概率已经有一两个 Agent 在转了，只是没人特意告诉你。

我最近半年一直在做 Agent 相关的工程，踩的坑比写过的博客还多。今天把一些想法系统地捋一遍——2026 年的智能体到底长什么样，哪些是真进展，哪些是还在骗自己，以及接下来一年我押注什么。

## 一、2026 年的 Agent 架构：分层已经稳定下来了

2024、2025 那两年，大家对“Agent 该怎么搭”基本是各写各的。2026 年再看，架构层面的共识已经收敛得差不多了：

- **编排层**：一个 orchestrator 负责规划、拆任务、决定什么时候调子智能体、什么时候直接回答。这一层通常用最强的模型。
- **执行层**：一堆职责单一的子智能体，各带自己的工具集和系统提示词。很多子任务用小模型就够了，甚至本地跑。
- **工具层**：MCP 基本成了事实标准。写一个 server，所有客户端都能用——这件事的意义被低估了，它把“每接一个模型就重写一遍工具”的地狱给终结了。
- **Agent 间通信**：A2A 这类协议把“智能体互相调用”变成了可寻址、可鉴权的事，不再靠手写胶水。
- **记忆与状态层**：这是最容易被糊弄、也最容易翻车的一层，后面单独说。
- **沙箱执行层**：写文件、跑命令、开浏览器的 Agent，必须在隔离环境里跑。2026 年“给 Agent 一台能随便折腾的 VM”已经是标配。

一个直观的变化：以前我们说“某个 Agent 很强”，指的是它的提示词写得好。现在说的是它的**工具边界划得清不清、上下文管理做得好不好、失败能不能恢复**。提示词只是其中一小块。

## 二、Prompt Engineering 死了，Context Engineering 上位

这是我今年感受最深的一点。

很多人还在把 Agent 的问题当成“提示词不够好”。但你真跑过一个长任务就会发现，模型本身的能力往往不是瓶颈——**瓶颈是上下文里塞了什么、什么时候塞、什么时候该丢**。

几个具体现象：

1. **上下文腐烂（context rot）**。任务跑到 30 步以后，早期的重要约束被淹没在几千行工具输出里，模型开始忘记最初的目标。这不是模型变笨，是信噪比掉了。
2. **工具输出是上下文杀手**。一次 grep 回来 800 行，一次 API 调用返回一大坨 JSON。你不会把整个数据库塞进提示词，但很多人就这么把工具输出全塞进去了。
3. **压缩是有损的，而且损失不可控**。简单的“总结一下历史”会把关键数字、ID、用户原话一起丢掉，然后 Agent 就开始编。

所以现在做得好的团队，基本都在一个专门的地方较劲：**上下文工程**。

具体手段无非这些，但每一项都有讲究：
- 工具层就先做一轮裁剪和结构化，别把原始输出直接甩给模型；
- 用确定性的代码去压缩确定性的信息，比如用代码统计日志，而不是让模型读日志；
- 把“必须永远记住的东西”从对话历史里拎出来，单独放在系统级区域，不参与压缩；
- 定期做“上下文检查点”，把阶段性结论固化下来，丢掉过程细节。

说白了，就是在有限的窗口里做**信息预算管理**。这件事更像系统工程，不像写作文。

## 三、记忆：Agent 最容易被忽视的地基

上下文窗口是短时记忆，那长时记忆怎么办？

2026 年的主流做法大概是分四层：

- **工作记忆**：当前任务的上下文，用完就丢。
- **情景记忆**：发生过什么——“上个季度用户抱怨过这个 bug”，带时间戳、带来源。
- **语义记忆**：沉淀下来的事实和规则——“这个客户对价格敏感”。
- **程序记忆**：怎么做事——“部署这个服务要先跑迁移脚本”。

关键不在于存，而在于**什么时候写、什么时候读、什么时候忘**。

我见过最多的错误是“什么都往里存”。结果记忆库变成垃圾场，检索回来的东西一半是噪音，反而干扰判断。写得进去、检索得出来，才叫记忆；写进去但检索不出来，那叫日志。

另一个坑是**记忆的写入时机**。让 Agent 自己在对话中途决定“这条要记住”，往往会记住一堆无关紧要的东西。更稳的做法是任务结束时用一个专门的步骤做记忆固化，甚至用另一条相对便宜的模型来抽取。相当于给 Agent 配了个“下班后写日记”的环节。

## 四、评估：别再用“感觉”判断 Agent 好坏

这是我今年最想说的一点。

2025 年的时候，很多团队的 Agent 评估就是：跑几个 case，看着还行，上线。然后线上出事，回去改提示词，再看着还行。循环往复，没有任何积累。

2026 年做得认真的团队，评估已经很工程化了：

- **轨迹级评估**，而不是只看最终答案。同一个正确答案，可能是走了一条正确的路，也可能是碰巧猜对了。前者可复现，后者不可复现。
- **黄金数据集**，从真实失败案例里长出来。每修一个 bug，就往里加一条。
- **回放环境**。把工具调用录下来，做确定性的重放，这样评估才可复现、便宜、快。
- **可观测性**。OpenTelemetry 的 GenAI 语义约定落地以后，Agent 的每一步——模型调用、工具调用、token、耗时、成本——都能进 trace。没有 trace 的 Agent 就是黑盒。

我的经验是：**评估做不好，Agent 就永远停在“demo 到生产”之间的那道坎上**。你没法优化你测不出来的东西。

## 五、成本与延迟：工程权衡回来了

早期大家不太在乎钱，跑通再说。2026 年不行了，一个长任务动辄几十次模型调用，账单是实打实的。

现在比较常见的做法：

- **模型路由**。不是所有步骤都需要最强模型。分类、抽取、格式化这些小活交给小模型，甚至规则。编排和复杂推理才用大模型。
- **并行化子任务**。多个独立的子智能体同时跑，比串行快得多，但要注意别把 token 预算炸掉。
- **缓存**。系统提示词、工具定义、稳定的前缀，尽量走 prompt caching，能省一截。
- **设预算上限**。给每个任务设 token、时间、工具调用次数上限，超了就优雅退出，而不是无限转圈烧钱。

延迟方面更现实一点：**用户能接受 Agent 慢，但不能接受它卡住不动**。所以流式的中间状态、进度反馈，比绝对速度更重要。

## 六、多智能体：老问题换了个皮

2025 年“多智能体协作”火过一阵，好像把一堆 Agent 放一起就能涌现出智能。2026 年冷静下来了。

真相是：**多智能体本质上是分布式系统，而分布式系统的问题一个都不少**——通信开销、错误传播、协调失败、状态不一致、调试地狱。

我现在的判断是：
- 任务能靠单 Agent 加好工具解决的，别上多 Agent；
- 需要多 Agent 的场景，往往是职责天然隔离，比如一个写代码一个审代码，或者不同部门各有权限边界，而不是“为了让它更聪明”；
- 多 Agent 之间**尽量传递结构化结果，而不是自由对话**。自由对话看着酷，但不可控、难评估、贵。

说白了，多智能体是个组织设计问题，不是模型能力问题。

## 七、安全：最不性感、最要命的一块

Agent 有了工具，就等于有了手脚。手脚能干活，也能闯祸。

2026 年还没解决的核心问题之一是**提示注入**。网页、邮件、文档里藏一句指令，Agent 读了就可能照做。这不是靠提示词能防住的，得靠架构：

- **最小权限**。Agent 能调的每个工具，权限都收到刚好够用。
- **危险操作人工确认**。转账、删数据、发邮件，必须过人类的手。
- **双向认证**。Agent 代表用户操作时，对方服务怎么确认“这真是用户授权的”？支付和身份协议这一年进展不少，但生态还在长。
- **审计**。每一步工具调用都要留痕，出事了能回溯。

这块没什么巧办法，就是老老实实按安全工程的规矩来。

## 八、未来 12 个月我押注什么

随便说几个，愿意被打脸：

1. **Agent 的“操作系统”层会成型**。统一的权限、记忆、评估、调度，慢慢从各家自研变成基础设施。
2. **小模型专精化**。不是所有 Agent 都要跑在云端大模型上，端侧和本地的小模型会吃掉相当一部分子任务。
3. **评估和可观测性会成为采购标准**。没有 trace、没有回放的 Agent 产品，企业不会买单了。
4. **“人在回路”会从兜底变成设计核心**。怎么让人类优雅地介入、审查、接管，而不是打断——这是个产品问题，也是技术问题。

## 写在最后

回头看看，智能体这两年的变化其实不神秘。它没有突然变聪明，而是**周围的工程基础设施终于跟上了**——协议统一了，工具标准了，评估可做了，安全被正视了。

真正难的从来不是“让模型调用一个函数”。难的是它在真实世界里跑上一百次、一千次，还能稳定、可控、能解释、出错了能兜住。这活儿一点都不酷，大部分时间是脏活累活。但正是这些脏活，把 2023 年的玩具和 2026 年的生产系统区分开了。

如果有人问我明年该学什么，我的答案很简单：**把上下文工程、评估和可观测性这三件事做扎实**。剩下的，交给时间。
